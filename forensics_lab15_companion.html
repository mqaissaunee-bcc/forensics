01Overview — what this lab is really teaching

The Internet of Things turned ordinary objects into witnesses. A smartwatch logs your heart rate, steps, location, and the notifications your phone pushed to it. A smart speaker stores the Wi-Fi networks it joined — name and passphrase in plain text — its wake word, and the account that owns it. This data can place a person at a location and time, reveal their habits, and recover secrets the user never meant to leave behind.

You'll analyze two real IoT images in FTK Imager — a Samsung smartwatch (Android/ext4) and an Amazon Echo Dot — navigating their Linux-style file systems, pulling SQLite databases and config files, and reading them in DB Browser for SQLite. You'll recover health profiles (birthdate, height, weight), pedometer and heart-rate logs, email notifications, favorite-app history, the Echo's Wi-Fi passphrase and BSSIDs, its wake word, and the owning Amazon account.

Two ideas carry the lab. First, IoT devices run Linux (ext4) and store evidence in SQLite + plaintext config — so your Autopsy/DB-Browser skills transfer directly, you just need to know which database holds what. Second, timestamps arrive in several epochs — Unix seconds, Unix milliseconds, Java-epoch milliseconds — and DB Browser's display-format tool is how you convert each column correctly. Get the epoch wrong and a birthdate or a Wi-Fi connection time lands years off.

03Walkthrough

Task 1Smartwatch: media and thumbnails

ext4 Android layout — photos synced from the phone, with deleted-image survivors in .thumb.

  1. FTK Imager → add Lab15-1.img → note the file system is NONAME [ext4] (Android/Linux). Expand to root.
  2. Open media > Images for synced photos; open the hidden .thumb > phone folder — thumbnails named by source extension, which can survive deletion of the original.

Task 2Smartwatch: health, email, app databases

SQLite is where the behavioral evidence lives — export and read it.

  1. Export com.samsung.shealth/data/.shealth.db (+ journal), com.samsung.wemail/.../.wemail.db, and com.samsung.w-launcher-app/.../.favorite_apps.db (each with its journal) to E:\FOR_LAB_015\Exports\Lab15_1.
  2. In DB Browser, open .shealth.db → Browse Data → shealth_profile: age, birthday, height, weight, profile-creation date. Convert birthday via right-click → Edit display format → Java epoch (milliseconds) to date.
    📸Screenshot for your report: The shealth_profile table with the birthday converted to a readable date.
  3. Open shealth_pedometer_history (walking/running, steps, distance, calories by date) and shealth_heartrate_log (avg/min/max heart rate, start/end in epoch).
  4. Open .wemail.db → EmailAccountInfo (the account address) and EmailNotiInfo (notification title/body/sender — message fragments). Convert mDateTime via Unix epoch to date (a different epoch than the health DB).
    📸Screenshot for your report: The EmailNotiInfo table showing notification content and sender.
  5. Open .favorite_apps.db → app_item: most-recently-used apps (position 0 = most recent).

Task 3Echo Dot: Wi-Fi, wake word, account

Config files in plaintext plus a SQLite account store.

  1. Add Lab15-2.E01 → expand userdata (16) > NONAME [ext4] > [root] (ext4 again).
  2. Export data/com.amazon.imp/databases/map_data_storage_v2.db (+ journal) to E:\FOR_LAB_015\Exports\Lab15_2.
  3. Read misc/wifi/wpa_supplicant.conf in FTK's View pane: device codename/serial/model/OS, and the last Wi-Fi SSID + passphrase (plaintext) + last-connect time (Unix).
    📸Screenshot for your report: The wpa_supplicant.conf showing the SSID and plaintext passphrase.
  4. Read misc/wifi/networkHistory.txt (Hex view → Show text only): BSSIDs, validated-internet flag, auth method, gateway MAC, 2.4/5 GHz BSSIDs.
  5. Read davs/wakeword/models/.../op.cfg.json: the wake word (COMPUTER) and sleep command (STOP) — attribution via knowledge of the device's config.
  6. In DB Browser, open map_data_storage_v2.db → accounts table: the owning Amazon account/display name — ties the device to cloud data.
    📸Screenshot for your report: The Echo's accounts table showing the owning account.

04Reference — IoT evidence and epochs

Where IoT evidence lives

DeviceKey evidence
SmartwatchHealth profile (DOB/height/weight), step & heart-rate logs, email notifications, app usage, synced photos/thumbnails.
Smart speaker (Echo)Wi-Fi SSID+passphrase, BSSID/MAC history, wake word, owning account — and cloud voice data (via the account).
Commonext4 file system, SQLite databases, plaintext .conf/.json, journals (uncommitted changes).

Epoch conversions (the trap)

EpochBase / unitDB Browser format
Unixseconds since 1970Unix epoch to date
Unix msmilliseconds since 1970Unix epoch (ms)
Java epochmilliseconds since 1970Java epoch (milliseconds) to date
Watch out

Different columns in the same device use different epochs — the health DB here uses Java-epoch ms while the email notifications use Unix. Convert each column by its actual epoch, not a blanket guess.

05Where people get stuck

Most problems in this lab fall into one of these.

SymptomLikely causeFix
Converted date is wildly offWrong epoch chosenTry Unix seconds vs Unix ms vs Java ms — the right one yields a sensible date. Columns in one DB can differ.
Can't open the exported DBJournal not exported alongsideExport the -journal/-wal file too so DB Browser sees a consistent state.
File system looks unfamiliarIt's ext4, not NTFSIoT/Android devices use ext4 — same FTK navigation, Linux folder names (data, misc, root).
Passphrase looks garbledViewing binary as textIn FTK, switch to Hex view and 'Show text only' for config files; .conf is plain text.
Table seems emptyWrong table selectedUse the Table dropdown in Browse Data — the evidence is in a specific table, not the default one.

07Making it defensible

IoT data is intimate and device-version-specific — precision and provenance are everything:

  • Attribute to the account/device, then the person. A health profile or account ties data to a device and account; linking to a human needs corroboration.
  • Document which epoch you used per column. A misconverted DOB or connection time is a factual error that undermines the whole report.
  • Note what's on-device vs cloud. Be clear that the richest IoT evidence (voice, full history) often lives in the cloud and wasn't examined here.
  • Hash exported databases (Lab 20) and record the exact source path; version-specific schemas mean your path documentation is how others reproduce your work.
On the stand

IoT evidence can feel uncannily specific ('his watch says he ran at 2 a.m.'). The defense will probe device/app version differences, clock accuracy, and whether the account owner is the person. Pin the epoch, cite the source DB, and distinguish device/account from individual.

09Check yourself

1. What file system do most IoT and Android devices use, and why does that help you?

ext4, the Linux file system. Your existing FTK/Autopsy navigation and SQLite skills transfer directly — you just learn the Linux folder names (data, misc, root) and which app database holds the evidence.

2. The same device stores one timestamp in Java-epoch milliseconds and another in Unix seconds. What's the risk, and how do you handle it?

Converting a column with the wrong epoch produces a date off by years or decades. You must identify and convert each column by its actual epoch (e.g. DB Browser's 'Java epoch (ms) to date' vs 'Unix epoch to date'), not apply one conversion blindly.

3. What sensitive, directly usable evidence can an Echo Dot's wpa_supplicant.conf yield, and what's its forensic value?

The last Wi-Fi SSID and its passphrase in plain text, plus the last-connection time. It can tie the device to a specific router (and thus a location) at a time, and — because people reuse passwords — may be a lead toward other accounts. It's sensitive and must be handled within legal authority.

4. Why might the data you recover from an Echo on-device be only a small part of the picture?

Smart speakers store most of their evidence — voice recordings, interaction history, timelines — in the cloud on the vendor's servers, reachable only through the account and legal process. On-device data (account, Wi-Fi, wake word) is the tip of the iceberg.
