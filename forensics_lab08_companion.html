01Overview — what this lab is really teaching

A file can tell you more by its context than its content. A Windows .lnk (shortcut/link) file is automatically created when a user opens a document — and it records the full path of the target, the volume it lived on (serial number, name, type), the file's size and MAC times, and even the network path, NetBIOS name, and MAC address of a remote machine the file came from. Embedded document metadata adds author, title, revision count, application, edit time, and — crucially — its own creation/modified dates that may contradict the file system's.

You'll export link files from the Recent folder with FTK Imager, parse them with Lnk Examiner, then pull embedded metadata from a batch of documents with MetaExtractor — and read the story the two kinds of metadata tell together.

The central distinction: file-system metadata (MAC times, owner) describes the file's life on this volume and is comparatively easy to alter; embedded metadata (author, internal timestamps, $I30 index attributes) travels inside the file and is harder to fake. When the two disagree — e.g. a modified date earlier than a creation date — that contradiction is itself evidence: usually that the file was created elsewhere and copied, or that the system clock was manipulated.

03Walkthrough

Task 1Export link files

The Recent folder is a trove of .lnk files, one per recently opened item.

  1. FTK Imager → add Lab8-1.E01 → expand to Documents and Settings\Mr. Evil\Recent.
  2. Click a .lnk (e.g. yng13.lnk) → Properties tab: FTK already shows target MAC times, owner SID/RID, and $I30 INDX attributes (NTFS index records with reliable timestamps).
    📸Screenshot for your report: A .lnk file's Properties showing its target MAC times.
  3. Ctrl-select all the .lnk files → Export Files → E:\FOR_LAB_008\Link_Files\.

Task 2Parse them with Lnk Examiner

Lnk Examiner tabulates the rich data inside each shortcut.

  1. Open DART → Forensics → Windows Forensics → Lnk Examiner → Start as Admin.
  2. Process → Folder → Link_Files. The table fills with: target path, creation/modified/access times (from $I30), file size, attributes (directory/archive/read-only), volume type/serial/name, and for remote files the network path, NetBIOS name, and MAC address.
    📸Screenshot for your report: The Lnk Examiner table showing target paths and volume serials.
  3. Two entries here were opened from a network share \\4.12.220.254\TEMP — hence no local volume serial, but a network path and MAC instead.
  4. Export → Save as CSV to E:\FOR_LAB_008\Lnk_Report\.

Task 3Export documents for metadata analysis

A spread of real document types with telling internal metadata.

  1. FTK Imager → Remove All Evidence Items → add Lab8-2.E01 → expand RICHARDUSB [FAT16]\root.
  2. Ctrl-select the sample docs (XLS, several PDFs, a DOCX) → Export Files → E:\FOR_LAB_008\Metadata_Analysis\.

Task 4Extract embedded metadata with MetaExtractor

Author, internal dates, application, revisions — and the file-system contradiction.

  1. Open MetaExtractor.exe → Open Folder → Metadata_Analysis.
  2. Note the first columns show file-system metadata where modified dates PRE-date creation dates — the signature of files created elsewhere and copied here.
  3. Scroll to Author (e.g. 'Connor Cleak'), Title (an .indd source reveals a PDF was made from Adobe InDesign), embedded Created/Modified (trust these over file-system dates), Last Modified By, Revision, Application Name, and Last Printed.
    📸Screenshot for your report: The MetaExtractor Author/Created/Modified columns showing the date contradiction.
  4. Save to CSV in E:\FOR_LAB_008\Metadata_Report\.

04Reference — two kinds of metadata

File-system metadataEmbedded metadata
LivesIn the MFT / directory entryInside the file's own structure
ExamplesMAC times, owner SID, size, attributesAuthor, title, internal dates, revision, app, edit time, last printed
ScopeThis file on this volumeTravels with the file across volumes
ReliabilityEasier to alter (touch, copy, clock change)Harder to fake — prefer it when the two conflict

What a link file records

  • Target path and the volume it lived on: type (fixed/CD-ROM/removable), serial number, and label.
  • Target's MAC times and size, pulled from $I30 index attributes.
  • For remote targets: network path, NetBIOS/computer name, and MAC address of the source machine — proof the file came from a specific device.
  • It persists even after the target is deleted — evidence a file was opened when the file itself is gone.

The contradiction that matters

When embedded Created > embedded Modified, or when file-system Modified pre-dates Created, something is off: typically the file was authored on another machine and copied (file-system dates reset on copy), or the system clock was manipulated. Either way, the mismatch is a finding, not noise.

07Making it defensible

Metadata tells stories, but stories can be challenged — so corroborate and qualify:

  • Use both metadata types together. The power is in the contradiction, not either source alone.
  • Prefer embedded over file-system dates when they conflict, but say why — file-system dates reset on copy and are easier to alter.
  • A link file is strong placement evidence. It can put a specific document, from a specific volume or remote host, in front of a specific user — corroborate with registry (Lab 4) and timeline (Lab 14).
  • Don't over-read absence. No 'Last Printed' value means no record, not proof it was never printed.
On the stand

Metadata is a favorite defense target ('anyone could have changed that date'). Your defense is corroboration: the .lnk, the registry RecentDocs, the timeline, and the embedded author all pointing the same way.

09Check yourself

1. What can a link file prove about a file that no longer exists on the system?

That the file was opened on this machine, where it lived (full path, volume serial/type/name), its size and MAC times, and — if remote — the network path, NetBIOS name, and MAC of the source device. The .lnk persists after the target is deleted.

2. A document's modified date is earlier than its creation date. What's the most likely explanation?

The file was created on a different machine and copied here — file-system creation date is set at copy time, while the modified date carried over from the original. (Clock manipulation is the other possibility.) Either way the contradiction is evidence.

3. Why prefer embedded metadata over file-system metadata when they disagree?

Embedded metadata travels inside the file and is harder to alter; file-system metadata is easier to change (via touch, copying, or clock changes) and is reset by ordinary operations like copying. So embedded dates are generally more reliable.

4. A .lnk has a network path and MAC address but no volume serial. What does that tell you?

The target file was opened from a network share rather than a local volume, so there's no local volume serial — instead you get the share's path, the source computer's NetBIOS name, and its MAC address.
