Overview — what this lab is really teaching

Proving a file was accessed can matter as much as the file itself. This lab mines two kinds of metadata: the system metadata in Windows link (.lnk) files — which record where a referenced file lived, what volume it was on, even a remote IP and MAC — and the embedded metadata inside documents (author, created/modified dates, the app that made them, last printer).

The sharp insight: embedded metadata is usually more trustworthy than file system metadata, because it's harder to fake. When the two conflict, the discrepancy is itself evidence — often of clock tampering or a file created elsewhere and copied in.

Tools & environment

On WinOS: FTK Imager to export files, Lnk Examiner (in DART) to parse shortcuts, and MetaExtractor (4Discovery) to pull document metadata to CSV.

Metadata sourceRepresentative fields
Link file (.lnk)Target path, created/accessed/modified, file size, volume type/serial/name, network path, NetBIOS name, MAC address
$I30 index attributes (NTFS)Accurate create/access/modify from the directory index
Document (Office/PDF)Author, title, created/modified, last-modified-by, revision, app name, char/word/page counts, last printed

Walkthrough

Task 1 — Link files

1 Export the .lnk files

Load Lab8-1.E01, navigate to Documents and Settings > Mr. Evil > Recent (a folder of shortcuts to recently opened files), and export all the .lnk files to E:\FOR_LAB_008\Link_Files. Note FTK Imager already shows file-system dates in the Properties tab, plus $I30 index attributes (lines starting INDX).

2 Parse them in Lnk Examiner

In DART > Forensics > Windows Forensics > Lnk Examiner, Process > Folder → your Link_Files folder. The table fills with target paths, $I30-derived timestamps, file sizes, volume type/serial/name, and — for network-opened files — the network path (\\IP\share), NetBIOS name, and MAC address. Export to CSV.

Why a shortcut is a goldmine

A .lnk persists even after the original file is gone, and records the volume and often the machine the file lived on. Two files here were opened from \\4.12.220.254\TEMP — the shortcut captured the exact IP and share.

Task 2 — Document metadata

3 Export a set of documents

Remove the first image, load Lab8-2.E01, open the RICHARDUSB [FAT16] root, and export the listed PDFs/DOC/XLS to E:\FOR_LAB_008\Metadata_Analysis.

4 Pull metadata with MetaExtractor

Run MetaExtractor > Open Folder → Metadata_Analysis. Read across: file-system dates, MD5, Author, Title, embedded Created/Modified, Last Modified By, Revision, Application Name, and Last Printed. Save to CSV.

When dates disagree, trust the embedded ones

Why it matters in court

Metadata ties people, files, devices, and time together

A .lnk can place a file on a specific volume or remote machine; document metadata can name the author and reveal a doctored timeline. These links are often what turns 'a file was present' into 'this person did this.'

  • Embedded over file-system when they conflict — and the conflict itself is evidence.
  • Volume serials connect back to the file-system work in Lab 05.
  • Corroborate. Cross-check metadata against registry MRUs and timeline.

Course relevance

Core to Module 9 (Analysis and Validation) and Module 5. Distinguish file-system vs embedded metadata, know what .lnk files capture, and why embedded dates are more trustworthy.

Check yourself

1. A document's embedded 'modified' date is earlier than its file-system 'created' date. What does that suggest?

The file was created on another device and copied onto this volume (or the system clock was manipulated). The embedded date is the more reliable record, and the discrepancy is itself evidence.

2. A link file has no volume serial but lists a network path and a MAC address. What does that tell you?

The referenced file was opened from a network location, so the .lnk recorded the remote share's IP/path, the host's NetBIOS name, and its MAC instead of a local volume serial.

3. Why is embedded metadata generally more trustworthy than file-system metadata?

It's written inside the file by the application and is harder to alter than file-system timestamps, which change with ordinary copy/move operations and can be manipulated.

4. A document's 'Last Printed' field is empty. Does that prove it was never printed?

No — it only means there's no print record stored in the file. It could have been printed without the metadata recording it.
