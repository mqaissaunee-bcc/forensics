Overview — what this lab is really teaching

RAM holds things a disk never will: running processes, open network connections, decryption keys, injected malware, chat windows that were never saved. It's also volatile — pull the power and it's gone. This lab is memory forensics: capture RAM, then analyze it.

The tension to understand is order of volatility. Because acquiring RAM means running a tool on the live system, you unavoidably change it slightly. You accept that small footprint in exchange for data that would otherwise vanish — and you document exactly what you ran.

Tools & environment

All on the WinOS VM:

ToolRole
Magnet Process CaptureDumps selected running processes (and their RAM) to .dmp files.
Magnet RAM CaptureLightweight full-memory acquisition to a .raw image; tiny footprint.
FTK ImagerManually carves a JPEG out of a memory dump to show what's recoverable.
Redline (FireEye)Incident-response analysis of a memory image — processes, drivers, timeline.
Why RAM can't be hash-verified like a disk

A live system changes memory constantly, so you can't re-read it to the same hash. Instead you hash the captured file afterward and store that hash with the image to prove the capture hasn't changed since.

Walkthrough

Task 1 — Capture specific processes

1 Export the svchost processes

Open Magnet Process Capture, check the svchost processes, point the output to E:\FOR_LAB_002\LAB_002_Running_Processes, and click Start. Warnings that a process is no longer running are normal — processes come and go while you work.

Task 2 — Capture full RAM

2 Image memory with Magnet RAM Capture

Point the save path to E:\FOR_LAB_002\FOR_LAB_002_RAM_Capture, set a 500 MB segment size, and Start.

Why 500 MB segments

Segmenting keeps each file under the FAT32 4 GB ceiling, so your capture survives being written to USB media that's formatted FAT32.

Pod cleanup step

The lab asks you to delete the .raw you create afterward — the pod has limited space and a pre-made dump is used for analysis. Don't skip the cleanup or later steps may fail.

Task 3 — Carve a file out of memory

3 Load the prepared dump in FTK Imager

Add memdump.mem (Desktop > Toolbox > Datasets > Lab2) as an image file, select it, and right-click the View pane > Fit to window.

4 Find a JPEG by its signature

Right-click > Find, choose Binary (hex), and search the JPEG header FF D8 FF E0. The matching text should read ýØýà . . JFIF.

File signatures (magic numbers)

Files announce their type with fixed starting (and often ending) bytes. JPEG = header FF D8 FF E0, footer FF D9. This is the foundation of all data carving (Lab 07).

5 Highlight header-to-footer and carve

Click-drag from the FF D8 FF E0 header to the FF D9 footer, then right-click > Save selection as Mem_001.jpg. Open it in IrfanView — if it renders, you carved a real image straight out of RAM.

The carved image (Mem_001.jpg) open in a viewer.

Task 4 — Analyze with Redline

6 Load the memory image into Redline

Open Redline > Analyze Data > From a Saved Memory File, point it at memdump.mem, name the analysis, store it under FOR_LAB_002_Analysis, and let it parse. Approve the UAC prompt for the Redline services if it appears.

7 Review processes, drivers, and timeline

In the Analysis Data pane, examine Processes (names, paths, SIDs, PIDs, parent PIDs — Show Details for more), Driver Modules (a classic place to spot a malicious driver), and the Timeline (events in chronological order).

Reference — what lives in memory

Artifact in RAMWhy you care
Running & terminated processesWhat was executing, including malware that never touched disk.
Loaded drivers / modulesRootkits and malicious drivers hide here.
Network connectionsActive C2 channels, open sockets, remote IPs.
Injected codeFileless malware that exists only in memory.
Credentials & keysPlaintext passwords, decryption keys for encrypted volumes.
Cached documents / imagesFiles viewed but never saved (as you carved here).
Order of volatility

Collect the most fleeting evidence first: CPU registers/cache → RAM → network state → running processes → disk → backups. RAM sits near the top, which is why it's captured early and live.

Why it matters in court

Document the live footprint

Because capturing RAM runs code on the evidence system, your notes about exactly which tool you ran, when, and why are part of the defensible record. The small, disclosed change is accepted; an undocumented one is a problem.

  • Memory evidence is often decisive — it's where fileless malware and live keys are, and nowhere else.
  • Hash the capture file immediately so you can later prove the dump is unchanged.
  • Prefer lightweight tools that leave the smallest footprint on the target.

Check yourself

1. Why can't you verify a RAM image the same way you verify a disk image?

A live system constantly changes memory, so you can't re-read RAM to reproduce the same hash. Instead you hash the captured file after acquisition and store that hash as your integrity record.

2. What header and footer identify a JPEG during carving?

Header FF D8 FF E0, footer FF D9.

3. Name two things you can recover from RAM that may not exist anywhere on disk.

Any two of: running/terminated processes, active network connections, injected/fileless malware, plaintext credentials or decryption keys, documents or images viewed but never saved.

4. Acquiring RAM necessarily alters the live system a little. How do you handle that forensically?

You accept the small footprint because the data is otherwise unrecoverable, use the lightest-touch tool available, and document precisely what you ran and when so the change is disclosed and defensible.
