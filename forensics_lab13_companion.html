01Overview — what this lab is really teaching

Where someone went online — and what they searched, downloaded, and were shown — is often the heart of a case. Browsers record it all in local databases: visit history, cookies that prove a site was actually reached, search terms, downloads, and cached images that let you see the very pages the user saw. This lab maps where each major browser hides that data and reads it both by hand and through Autopsy's parser.

You'll use Autopsy with the Recent Activity module to examine artifacts from Chrome (SQLite History + Cookies), Firefox (places.sqlite + cookies.sqlite), and Internet Explorer (the ESE WebCacheV01.dat), then view the cache folders as thumbnails to see rendered page images.

Three things make this lab land. First, each browser stores the same facts in a different place and format — you must know all three paths. Second, timestamps come in multiple epochs: Chrome counts microseconds from 1601, Firefox uses microseconds (history) or seconds (some fields) from 1970, so a raw number is meaningless until you know which clock it's on. Third, cache is the closest you get to seeing the user's screen — and a cookie or cache entry proves a site was genuinely loaded, not merely typed.

03Walkthrough

Task 1Chrome artifacts (SQLite)

Chrome keeps history and cookies in SQLite DBs under the user's Default profile.

  1. New case → add Lab13.E01 → tick only Recent Activity at ingest.
  2. Navigate Users\Mr Good\AppData\Local\Google\Chrome\User Data\Default\. The key files are History and Cookies.
  3. Click History → Application tab. Browse the urls table (url, title, visit_count, last_visit_time in Chrome time), visits (visit_time, from_visit = referrer, visit_duration in µs), keyword_search_terms, and downloads (path, size, source URL).
    📸Screenshot for your report: The Chrome urls table showing visited sites and counts.
  4. Click Cookies → cookies table: creation_utc, host_key (the site), expires_utc, last_access_utc. A cookie proves the site was actually reached.
  5. Open the Cache subfolder → Thumbnail view to see cached page images.

Task 2Firefox artifacts (SQLite)

Firefox splits storage: history/cookies under Roaming, cache under Local.

  1. History/cookies: ...\AppData\Roaming\Mozilla\Firefox\Profiles\*.default-release\.
  2. Open places.sqlite → moz_places (url, title, visit_count, last_visit_date) and moz_historyvisits (visit_date, from_visit, visit_type — an index where 3=bookmark, 7=download, 9=reload, etc.).
  3. Open cookies.sqlite → moz_cookies (name, value, host, expiry, lastAccessed, creationTime).
  4. Cache: ...\AppData\Local\Mozilla\Firefox\Profiles\*.default-release\cache2\entries → Thumbnail view.

Task 3Internet Explorer artifacts (ESE)

IE uses an ESE database and splits history/cookies/cache into separate folders.

  1. History: ...\AppData\Local\Microsoft\Windows\WebCache\WebCacheV01.dat (ESE database; the Recent Activity module already parsed it — browse the parsed rows: URL, referrer, title, program, domain, username).
  2. Cookies: the INetCookies folder (and its Low subfolder) — cookies stored as separate files with file-system MAC times.
  3. Cache: the INetCache\IE folders (alphanumeric subfolders; IE keeps file extensions) → Thumbnail view.

Task 4Review the aggregated parse

The payoff of running Recent Activity: one normalized, time-converted view.

  1. Results → Extracted Content → Web History: all browsers' history aggregated, timestamps already parsed.
    📸Screenshot for your report: Autopsy's aggregated Web History under Extracted Content.
  2. Browse the other Extracted Content categories (Web Cookies, Web Downloads, Web Search) and confirm they match what you found manually.

Timestamp epochs — the trap

  • Chrome/WebKit time: microseconds since 1601-01-01 UTC. A huge number like 13,250,000,000,000,000.
  • Firefox (history): microseconds since 1970-01-01 UTC (Unix × 1,000,000). Firefox cookies creationTime uses the same Chrome/WebKit base in some fields — read the column meaning.
  • Unix time: seconds since 1970 — common elsewhere.
  • A raw timestamp is meaningless until you know its epoch and multiplier. Use a tool like DCode, or let Autopsy convert — then verify the conversion.

Why cookies and cache matter

  • A cookie is near-proof a site was actually loaded (not just a typed URL) — the site wrote it to disk.
  • Cache images let you see what the user saw, even for pages no longer online.
  • visit_count / typed_count / from_visit distinguish a deliberate typed visit from a redirect or a single accidental hit.

06Manual corrections & currency notes

The NDG manual was written in 2020–21. These are the places where it is wrong, inconsistent, or out of date — worth knowing before you trust a screenshot.

WhereThe manual saysWhat's actually true
Browser lineupChrome, Firefox, Internet ExplorerIE is retired. Modern Edge is Chromium-based, so it stores history/cookies in the same SQLite schema as Chrome under its own profile path — your Chrome skills transfer directly. The old ESE WebCache format is legacy.
Timestamp conversionPoints to DCodeDCode (Digital Detective) still works, but Autopsy, the Eric Zimmerman tools, and plugins now auto-convert. The point stands: always know the epoch.
Cache format driftDescribes older cache layoutsChrome's cache format has evolved (simple cache); current tools (Hindsight, ChromeCacheView) parse it. The evidentiary value — seeing cached pages, proving visits — is unchanged.
Sync / cloud historyTreats history as local-onlyModern browsers sync history/cookies to the cloud account — so a device may hold history from other devices, and the full picture may require the account. A nuance the lab predates.

07Making it defensible

Browser artifacts are rich but easy to over-read — precision about what each one proves is everything:

  • A visited URL is not an intentional visit. Use typed_count, visit_count, and from_visit (referrer) to distinguish a deliberate action from a redirect, ad, or auto-load.
  • Get the epoch right. A misconverted timestamp can put an event on the wrong day — verify conversions, don't just trust them.
  • A cookie/cache entry proves the site loaded — stronger than a typed URL, which may never have resolved.
  • Attribute to the account/profile, then to the person. History under 'Mr Good's' profile means that profile; tie it to a human with login and other evidence. And remember synced history may originate on another device.
On the stand

'A URL in the history doesn't mean my client typed it or saw it.' Often true — so lead with the artifacts that show intent (typed_count, referrer chains, cached renders, cookies) rather than a bare URL, and be candid about what each one does and doesn't establish.

09Check yourself

1. Where does Chrome store browsing history, and what format is it?

In a SQLite database named History inside the user's Default profile folder (AppData\Local\Google\Chrome\User Data\Default). Key tables include urls, visits, keyword_search_terms, and downloads.

2. A Chrome timestamp reads about 13 quadrillion. What epoch is that, and how do you interpret it?

Chrome/WebKit time: microseconds since 1601-01-01 UTC. You convert from that base (or let Autopsy do it and verify) — it is not Unix time, so treating it as seconds-since-1970 would give a wildly wrong date.

3. Why is a cookie stronger evidence of a visit than a URL in the history?

A cookie is written to disk by the site itself, so its presence shows the site was actually loaded and interacted with the browser. A URL in history can be a redirect, an auto-loaded resource, or a typed address that never resolved.

4. Modern Edge is Chromium-based. What does that mean for your analysis skills?

Edge stores history and cookies in the same SQLite schema as Chrome (in its own profile path), so the Chrome tables and techniques transfer directly. The legacy IE ESE WebCache format is no longer the norm.
