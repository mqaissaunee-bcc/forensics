01Overview — what this lab is really teaching

A hash is a file's fingerprint: run the file's bytes through an algorithm (MD5, SHA-1, SHA-256) and get a fixed-length value that changes completely if even one bit of the file changes. Hashing is the mathematical backbone of digital forensics — it's how you prove an image is unaltered (Lab 1's verification), how you find known files regardless of their name, and how you filter out millions of innocuous system files so you can focus on what matters.

You'll generate hash lists with FTK Imager (MD5/SHA-1) and Hasher (SHA-256/512 and more), compare algorithms, then build a hash set in Autopsy and run it against an image — watching Autopsy find files whose names and extensions were changed but whose content (and therefore hash) is identical to your known set.

Two properties make hashing work. Determinism: the same input always yields the same hash, so a file's identity travels with its content, not its name — rename evidence.jpg to boring.dll and its hash is unchanged, which is exactly how a hash set catches disguised files. Avalanche: a one-bit change produces a wildly different hash, so any tampering is instantly visible. The caveat worth internalizing: MD5 and SHA-1 are broken for collision resistance (you can craft two different files with the same hash), so modern integrity work uses SHA-256 — even though MD5/SHA-1 remain common for known-file matching where deliberate collisions aren't the threat.

04Reference — algorithms and the two uses of hashing

AlgorithmSizeStatus
MD5128-bitCollision-broken. Still used for known-file matching; not for integrity against a motivated adversary.
SHA-1160-bitCollision-broken (2017). Being retired; same caveat as MD5.
SHA-256256-bitCurrent standard for integrity. Use this for image verification today.
SHA-512512-bitStronger SHA-2 variant.

Two jobs hashing does

  • Integrity / verification (Lab 1): acquisition hash == read-back hash proves nothing changed. Any alteration flips the hash (avalanche).
  • Known-file matching / filtering: compare file hashes against a set. Notable sets flag contraband/IP regardless of name; Known sets (e.g. the NSRL of standard OS/app files) let you ignore millions of innocuous files and focus your exam.

The two properties

  • Deterministic: same bytes → same hash, always. Identity travels with content, not name.
  • Avalanche: one-bit change → completely different hash. Tampering is instantly visible.
  • Watch out

    Collision caveat: MD5/SHA-1 can be made to collide deliberately — two different files, same hash. For integrity against an adversary, use SHA-256. For matching known files (no attacker crafting collisions), MD5/SHA-1 are still practical.

06Manual corrections & currency notes

The NDG manual was written in 2020–21. These are the places where it is wrong, inconsistent, or out of date — worth knowing before you trust a screenshot.

WhereThe manual saysWhat's actually true
Algorithm guidancePresents MD5/SHA-1 as fine for everythingFor integrity against a motivated adversary, MD5 and SHA-1 are unsafe (demonstrated collisions) — use SHA-256. They remain practical for known-file matching, where no one is crafting collisions. The lab understates the distinction.
NSRL / known setsBuilds only a small Notable setReal exams load the NSRL (NIST's hash set of known OS/app files) as a Known set to filter out millions of innocuous files — often the single biggest time-saver in an exam. The lab shows the mechanism, not the scale.
Collision realityTreats a hash match as proof of identityAn MD5/SHA-1 match is overwhelmingly likely to mean identical content, but deliberate collisions exist — so for high-stakes identity, confirm with SHA-256 or a second algorithm. Dual-hashing (MD5+SHA-1, or +SHA-256) hedges this.
Hasher toolUses a small utility called HasherAny reliable hasher works — certutil -hashfile, PowerShell Get-FileHash (SHA-256 default), md5sum/sha256sum, or suite-native hashing. The concept matters more than the tool.

07Making it defensible

Hashing is the most trusted technique in forensics — use it correctly and it's nearly unassailable:

  • Hash early and record it. Image at acquisition (Lab 1), carved and exported files at recovery — a stored hash is how you later prove nothing changed.
  • Use SHA-256 for integrity against any adversarial scenario; dual-hash for extra assurance. MD5/SHA-1 are acceptable for known-file matching.
  • A hash match = identical content, independent of name — that's its power and how you defeat renaming/disguise. State it as a content match, not a 'same file' assumption, if deliberate collision is a live concern.
  • Document your hash sets. Which set, Known or Notable, where it came from (e.g. NSRL) — the filtering you did is part of a defensible method.
On the stand

Hashing is the examiner's strongest card: 'the hash at acquisition equals the hash now, so the evidence is unchanged.' Pair it with SHA-256 for integrity, be candid that MD5/SHA-1 collisions exist, and present a hash-set match as proof of identical content — which is exactly what defeats a 'but I renamed it' defense.

09Check yourself

1. What two properties of a hash function make it the backbone of forensic integrity, and what does each guarantee?

Determinism — the same input always produces the same hash, so a file's identity is tied to its content, not its name. And the avalanche effect — a one-bit change produces a completely different hash, so any alteration or tampering is immediately visible.

2. How does a hash set catch a file that a user renamed from evidence.jpg to system32.dll?

Hashing ignores names, extensions, and timestamps — it's computed from the file's bytes. The renamed file has the same content, so the same hash, and it matches the hash set regardless of the disguised name or extension.

3. Why are MD5 and SHA-1 unsuitable for integrity against a motivated adversary, yet still used in forensics?

Both are collision-broken: an attacker can craft two different files with the same hash, so a match no longer guarantees identical content against a deliberate adversary — SHA-256 is used for integrity instead. But for matching against sets of known files, where no one is crafting collisions, MD5/SHA-1 remain fast and practical.

4. What's the difference between a 'Known' hash set and a 'Notable' hash set, and give a real-world example of each.

A Known set marks files to ignore — e.g. the NSRL of standard OS/application files, used to filter out millions of innocuous files. A Notable set flags files of interest — e.g. known contraband or stolen-IP hashes, used to surface matches. They do opposite jobs: one hides, one highlights.
