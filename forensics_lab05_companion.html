01Overview — what this lab is really teaching

Under every file name and folder icon is raw structure: a partition table that says where volumes live, and a file system that says how data inside a volume is organized. This lab takes you down to the bytes — reading the Master Boot Record and Volume Boot Record by hand in a hex editor to identify FAT, NTFS, and exFAT volumes and pull out serial numbers, sizes, and cluster geometry.

You'll use HxD to navigate by offset, decode little-endian values in the Data Inspector, and read the specific bytes that reveal each file system's identity. The payoff isn't memorizing offsets — it's understanding why a tool reports a volume as NTFS, so that when a tool is wrong, or when someone has deliberately corrupted a boot sector to hide a volume, you can verify the ground truth yourself.

Two mechanics make everything click. Offsets: the MBR is sector 0; partition entries start at byte 446; the VBR here starts at sector 63 (offset 63 × 512 = 32256). Little-endian: multi-byte numbers are stored low-byte-first, so 86 39 01 00 is read as 00 01 39 86 = 80262. Miss the byte-reversal and every value you compute is wrong.

03Walkthrough

The flow is the same for all three file systems: read the MBR partition entry to learn the file-system type byte and where the VBR starts, jump to the VBR, then read the identity bytes. Set View > Offset base > Decimal so the offsets below match what you type.

Task 1Read the MBR partition table (FAT image)

The partition table is 64 bytes at offset 446, four 16-byte entries. One entry tells you the file-system type and the VBR's starting sector.

  1. Tools > Open disk image → NDG FAT Lab5.001 → sector size 512.
  2. Search > Go to (Ctrl+G) → offset 446 (dec). Highlight 16 bytes — that's partition entry 1.
  3. Decode it: byte 0 = active flag (80=bootable), byte 4 = type (0E=FAT), bytes 8–11 = starting sector (little-endian → 3F = 63), bytes 12–15 = sector count.
    📸Screenshot for your report: The highlighted 16-byte partition entry with the Block length showing in the status bar.
  4. Boot signature 55 AA sits at bytes 510–511 — the MBR's 'this is valid' marker.

Task 2Read the FAT VBR

Sector 63 = offset 32256. From there, fixed offsets give you the file system's identity.

  1. Go to offset 32256. The first 3 bytes are the jump instruction; the next 8 are the OEM ID (MSDOS5.0 → FAT).
  2. Bytes-per-sector (offset +11), sectors-per-cluster (+13) → multiply for cluster size (512 × 2 = 1024).
  3. Media descriptor (+21): F8 = fixed/removable disk. Total sectors (+32), volume serial (+39), FS type string FAT16 (+54).
    📸Screenshot for your report: The VBR with the FAT16 file-system type string highlighted.

Task 3Read the NTFS VBR

Same layout, different identity bytes — and the pointer to the Master File Table.

  1. Open NDG NTFS Lab5.001. The partition type byte is now 07 (NTFS/exFAT). VBR still at sector 63.
  2. OEM ID at +3 reads NTFS. Sectors-per-cluster is 8 here → cluster size 4096.
  3. At offset +48 is the starting cluster of the MFT (here 3344) — where every file's metadata lives. Volume serial is at +72.

Task 4Read the exFAT VBR

A third identity, with sizes stored as powers of two.

  1. Open NDG exFAT Lab5.001. Type byte is also 07 — so the OEM ID is what distinguishes it: EXFAT at +3.
  2. exFAT stores bytes-per-sector and sectors-per-cluster as 2^N: a stored value of 9 means 2^9 = 512 bytes/sector; a stored 3 means 2^3 = 8 sectors/cluster.
  3. Volume length (+72) and volume serial (+100) round out the identity.

The two mechanics you can't skip

  • Offset math: sector × 512 = byte offset. Sector 63 = 32256. A VBR field at sector-relative byte 54 is at absolute offset 32256+54 = 32310.
  • Little-endian: reverse the byte order before converting. 86 39 01 00 → 00 01 39 86 → 80262. Volume serials are also little-endian (shown reversed).
  • Type byte 07 is ambiguous — both NTFS and exFAT use it. Always confirm with the OEM ID.

06Manual corrections & currency notes

The NDG manual was written in 2020–21. These are the places where it is wrong, inconsistent, or out of date — worth knowing before you trust a screenshot.

WhereThe manual saysWhat's actually true
File-system coverageCovers FAT, NTFS, exFATCurrent and relevant. The modern gaps worth naming: APFS (macOS, Lab 7's cousin), ext4 (Linux/Android, seen in Labs 15–16), and ReFS (Windows Server). Same MBR/VBR logic, different structures.
MBR vs GPTReads an MBR partition tableMBR is legacy (4 primary partitions, 2 TB limit). Modern disks use GPT, which keeps a protective MBR at sector 0 for compatibility but stores the real partition table in GPT headers. Recognize both.
'Each entry is 16 bytes, max 4 partitions'Stated as a hard limitTrue for the primary MBR table. The historical workaround is an extended partition holding logical partitions — the lab mentions but doesn't explore this.
FAT relevanceSpends the most time on FATFAT/exFAT are very much alive on USB drives, SD cards, and camera media — so this isn't just history. But NTFS is where most Windows evidence lives.

07Making it defensible

Reading structure by hand is what lets you catch deception and tool error:

  • Verify, don't trust the icon. A deliberately corrupted boot sector can make a volume 'disappear' from tools. Reading the raw bytes recovers the truth.
  • Show your math. If you state a volume is 41 MB, be able to show sectors × sector size. Reproducibility is the standard.
  • Cite the byte. 'The OEM ID at offset +3 reads NTFS' is a verifiable claim; 'the tool said NTFS' is a secondhand one.
  • Record the volume serial. It's created at format time and can tie a file (via link files, Lab 8) back to the exact volume it lived on.
On the stand

Byte-level analysis is the antidote to 'the tool could be wrong.' You can show the examining attorney the actual bytes and the arithmetic — that's as reproducible as forensics gets.

09Check yourself

1. The partition type byte is 07 on two different images. How do you tell NTFS from exFAT?

Type byte 07 covers both. Read the OEM ID at VBR offset +3: 'NTFS' versus 'EXFAT' is what distinguishes them.

2. The bytes 86 39 01 00 store a sector count. What's the value and why?

80262. The value is little-endian, so you reverse to 00 01 39 86 before converting from hex to decimal.

3. A volume's VBR starts at sector 63. What byte offset is that, and why does it matter?

63 × 512 = offset 32256. You add the field's sector-relative offset to 32256 to reach any VBR field, so getting the sector-to-byte math right is the basis of everything else.

4. exFAT stores a sectors-per-cluster value of 3. How many sectors per cluster is that?

exFAT stores it as a power of two: 2^3 = 8 sectors per cluster.
