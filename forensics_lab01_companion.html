01Overview — what this lab is really teaching

Everything downstream — every hash you compute, every file you carve, every timeline you build — rests on one thing: a bit-for-bit copy of the original media that you can prove you did not change. This lab is where that copy is made.

You will use FTK Imager to acquire both a physical image (the whole drive, including unallocated space and slack) and a logical image (one partition), store them in the E01 / Expert Witness Format, and let the tool verify them by comparing the acquisition hash with a read-back hash. The verification pass is the lab's whole point: a forensic image is not forensic until something has proven it matches the source.

The one habit to build here: a write blocker sits between you and original evidence always. The lab simulates clean source media, so nothing bad happens if you forget — but in the field, mounting a suspect drive read/write updates last-access times and can make the evidence inadmissible before you have imaged a single byte.

03Walkthrough

FTK Imager is a GUI tool, so this walkthrough names the windows and buttons rather than commands. Read the Reference section for what each image format and option actually does.

Task 1Learn the interface

  1. Launch FTK Imager from Start > AccessData > FTK Imager (or the desktop icon).
  2. Find the four panes: Evidence Tree (added items), File List, Properties, View (hex/text). You'll live in these all semester.
  3. Open the File menu and note Create Disk Image, Add Evidence Item, Verify Drive/Image, and Capture Memory — the four operations that cover acquisition, review, validation, and live RAM.

Task 2Create a physical image (E01, verified)

A physical image captures the entire drive, so it includes deleted files and unallocated space — always your first choice when you can get it.

  1. File > Create Disk Image → Physical Drive → Next.
  2. Select PHYSICALDRIVE1 → Finish. Watch out

    FTK Imager can appear to hang on this step. Do NOT click Next again — wait.

  3. In Create Image, tick Verify images after they are created and leave the others at default.
    📸Screenshot for your report: The Create Image window with Verify ticked.
  4. Click Add → choose E01 (Expert Witness Format) → Next.
  5. Fill in the Evidence Item Information accurately — your name goes in the Examiner field. This metadata is baked into the E01 and shows up in court.
  6. Browse to E:\, make a folder FOR_LAB_001, name the image, leave fragment size and compression at default, Finish → Start.
  7. When it finishes, read the Drive/Image Verify Results: the MD5 and SHA1 should match acquisition.
    📸Screenshot for your report: The Verify Results window showing matching MD5/SHA1 and zero bad blocks.

Task 3Create a logical image

A logical image captures one partition's live files only — the right choice when a full physical image isn't possible (huge drives, selective seizure, encrypted volumes).

  1. File > Create Disk Image → Logical Drive → Next.
  2. Select G:\ USB 001 [NTFS] → Finish, then repeat the E01 + Verify flow into a FOR-LAB-001A folder.

Task 4Verify the image two ways

An image you can't prove is clean is worthless. Confirm it through the report and by re-opening it.

  1. Open the image's .txt report in Notepad. Confirm the Computed Hashes match the verification results, and read the case info, drive model/serial, and acquisition times.
    📸Screenshot for your report: The .txt report's hash block, showing computed and verification hashes agree.
  2. Back in FTK Imager, File > Add Evidence Item > Image File, open your .E01, and expand the tree to root. If the file system mounts and you can browse it, the image is good. Repeat for the logical image.

04Reference — image formats & options

FormatWhat it isWhen to pick it
Raw (dd)Flat sector-for-sector dump, no compression, no embedded metadata.Maximum tool compatibility; when another tool needs raw input. Verify hash separately.
E01Expert Witness Format: compression, segmentation, embedded case metadata and a stored CRC/hash.The default forensic choice — self-documenting and self-verifying.
AFFAdvanced Forensic Format: raw data plus metadata in a companion file; open format.When you want an open, non-proprietary container.
SMARTLegacy format for the Linux SMART tool.Rarely — mostly historical.

Options worth understanding

  • Verify images after they are created — re-reads the image and re-hashes it. The whole reason you trust the copy. Leave it on.
  • Fragment size — splits the image into segments (.E01, .E02, …). Keep segments under 4 GB for FAT32 destinations.
  • Compression (0–9) — 0 is none (fastest), 9 is smallest (slowest). Hash integrity is unaffected either way.
  • Precalculate Progress Statistics — estimates time and checks you have enough destination space before you commit.
  • Add Overflow Location — a second destination if the first fills. Note: if you use it, uncheck Verify (FTK can't verify segments split across locations) and verify later with Verify Drive/Image.

05Where people get stuck

Most problems in this lab fall into one of these.

SymptomLikely causeFix
FTK Imager freezes after choosing Physical DriveNormal enumeration delay on the drive select stepWait it out. Clicking Next again queues a second action and can crash the dialog.
Hashes don't match on verifyA genuinely bad acquisition, or a flaky source/destinationRe-image. A mismatch means the copy is not trustworthy — never 'explain it away'.
Can't write to the destinationFull drive, or a read-only destinationCheck free space with Precalculate; confirm E: is writable.
Verify is greyed out / didn't runOverflow location was used, which blocks inline verifyFinish the image, then run File > Verify Drive/Image on the completed E01.
Path still says 'New Folder' after renamingWindows didn't commit the rename before the path was capturedRe-check the destination path on the Create Image screen before clicking Start.

06Manual corrections & currency notes

The NDG manual was written in 2020–21. These are the places where it is wrong, inconsistent, or out of date — worth knowing before you trust a screenshot.

WhereThe manual saysWhat's actually true
Format choiceUses E01 for the exerciseCorrect and current — E01 remains the dominant forensic container. Raw (dd) is still the most portable if a tool chokes on E01.
MD5/SHA1 verificationPresents MD5 and SHA1 as the verification hashesBoth are cryptographically broken for collision resistance, but for proving an image hasn't changed they're still fine — and dual MD5+SHA1 is what courts expect. Newer acquisitions increasingly add SHA-256.
Write blockerSays a write blocker 'must be used' but the lab doesn't use oneThe lab uses safe source media so it's optional here. In the field it is non-negotiable on original evidence. Treat the reminder as the rule, not the exception.
FTK Imager versionScreenshots show an older AccessData buildFTK Imager is now maintained by Exterro; the acquisition workflow is unchanged, but menus may look slightly different from the manual's screenshots.

07Making it defensible

A forensic image is a legal artifact, not just a file. Three things make it hold up:

  • It was never written to. Write blocker on originals, always. The image is your working copy; the original goes back in the evidence locker untouched.
  • It verifies. Acquisition hash equals read-back hash, documented. If you later re-hash the image and it still matches, you've proven continuity of integrity.
  • It's documented. Examiner name, case number, drive make/model/serial, and acquisition timestamps live in the E01 metadata and your report — this is the start of the chain of custody you formalize in Lab 21.
On the stand

Expect to be asked, under oath, 'How do you know this is an exact copy of the drive you seized?' The answer is the matching hash pair and the verification report — not your word.

09Check yourself

1. Why is a physical image usually preferable to a logical one?

A physical image copies the entire drive — including unallocated space, slack, and deleted files — so it preserves artifacts a logical (live-files-only) image would miss. You take a logical image only when a physical one isn't feasible.

2. What does 'Verify images after they are created' actually do, and why does it matter?

It re-reads the finished image and re-computes its hash, then compares that to the hash taken during acquisition. A match proves the image is a faithful, unaltered copy of the source — the foundation of its admissibility.

3. You used an overflow location and now Verify is unavailable. What do you do?

FTK can't inline-verify an image split across multiple destinations. Finish the image, then run File > Verify Drive/Image on the completed E01 to hash and confirm it.

4. Why keep segments under 4 GB for a FAT32 destination?

FAT32 can't store a single file larger than 4 GB. Fragmenting the image keeps each segment under that limit so the destination can hold it.

11Cheat sheet
