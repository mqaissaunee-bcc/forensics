Overview — what this lab is really teaching

The first commandment of digital forensics: work on a copy, never the original. A forensic image is a bit-for-bit duplicate of a drive, hashed so you can prove in court it never changed. This lab builds that image with FTK Imager and then verifies it.

The judgment to internalize is the difference between a physical image (the whole disk, including deleted and unallocated space — the most complete and the preferred acquisition) and a logical image (one partition or volume, used when a full physical capture isn't possible). Both are court-admissible when hashed and documented; the physical simply contains more.

Why hashing is the whole point

An image without a hash is just a file. The MD5/SHA-1 computed during acquisition and compared after is what lets you testify the evidence is unaltered. Change one bit and the hash changes completely.

Tools & environment

You work entirely on the WinOS VM with FTK Imager (AccessData), a free acquisition and preview tool. Images are written to the Evidence Repository (E:) drive — never the drive you're imaging.

FTK Imager's interface has four panes: the Evidence Tree (added items), the File List, the Properties pane, and the View pane (raw text / hex of a selected file).

In the real world, a write-blocker comes first

The lab images a virtual drive directly, but in practice a hardware or software write-blocker sits between you and the original evidence so the acquisition process can't write a single byte back to it.

Walkthrough

Task 1 — Create a physical image

1 Open Create Disk Image

Log in to WinOS as Administrator / Train1ng$ and launch FTK Imager (Start > AccessData > FTK Imager). Choose File > Create Disk Image, select Physical Drive, and pick PHYSICALDRIVE1.

Be patient here

FTK Imager often appears to hang after you click Next on the source selection. Wait — do not click Next again or you'll queue a second action.

2 Choose the E01 format

Add a destination, then pick the image type. You'll use E01 (Expert Witness Format) — the forensic standard: it compresses, segments, and stores verification data and case metadata inside the image container.

FormatWhat it is
Raw (dd)Uncompressed full dump; stores no metadata about itself.
SMARTLegacy Linux SMART format; compression + segmentation, rarely used now.
AFFRaw image with metadata in a separate file; compresses and segments.
E01The common standard. Compression, segmentation, and embedded hashes + case info.

3 Fill in the evidence item information

Case number, evidence number, description, and — important — your name in the Examiner field. This metadata is written permanently into the E01 and shows up in the image report.

4 Set the destination and verify-on-create

Browse to Evidence Repository (E:), make a new folder FOR_LAB_001, name the image, and check Verify images after they are created. Leave segment size and compression at default.

The classic path trap

After you rename a new folder, FTK Imager often leaves the destination path reading New Folder. Confirm the real path before you start, or your image lands in the wrong place.

5 Start, then read the verify results

Click Start. When imaging finishes, the Drive/Image Verify Results window shows the MD5 and SHA-1 of the source compared with the image, plus any bad blocks. Matching hashes = a sound image.

Task 2 — Create a logical image

6 Image a single volume

Repeat File > Create Disk Image but choose Logical Drive and select the G:\ USB 001 [NTFS] volume. A logical image captures one partition's file system rather than the whole physical disk — useful when a full physical image isn't possible. Save it to FOR-LAB-001A, again with verification.

Task 3 — Verify the image two ways

7 Read the image report

In E:\FOR_LAB_001, open the .E01.txt report in Notepad. Confirm the case info you typed, the drive model and serial, acquisition start/end times, segment list, and that the computed hashes match the verification results.

8 Open the image back up

Use File > Add Evidence Item > Image File to load the E01, expand it down through the partition and file system to the root folder, and confirm the files are accessible. If root opens cleanly, the image is good.

Create a Physical Forensic Image A forensic image of original evidence is required to avoid changing valuable data and risk making the evidence found inadmissible in court. In this task, we will walk through the steps for creating a forensic image of a physical drive on the lab machine. The best image for forensic analysis is always a physical image as it contains the most data. There are cases when a logical image is necessary as well, and we will cover this later in the lab. It supports compression and segmentation but is not widely used anymore.  Advanced Forensic Format (AFF) - This format creates a raw image and stores the image metadata in a separate file. It supports compression and segmentation.  Expert Witness Format (E01) - This format is the most common forensic image type and supports compression and segmentation. It also stores data within the image container that can be used to help verify the image.

Reference — acquisition choices

ChoiceRule of thumb
Physical vs. logicalPrefer physical — it includes unallocated and deleted space. Use logical when a full physical capture isn't possible or isn't needed.
Image formatE01 for forensics (metadata + hashes inside). Raw/dd only when a plain bitstream is required by another tool.
Verify imagesAlways on. It's your proof of integrity.
Segment sizeKeep images on FAT32 media under 4 GB per segment; otherwise the default is fine.
Compression0 (none) is fastest; 6 is a good space/time balance. Compression never alters the data or its hash.
Overflow locationOnly if the destination may be smaller than the source — and then verification has to be done later, not inline.

Why it matters in court

The image IS the evidence

Every later analysis runs against this image, not the seized drive. Its credibility rests on two things: it was acquired without altering the original (write-blocker), and it can be proven unchanged since (hashing).

  • Integrity is provable, not assumed. The matching acquisition and verification hashes are what you point to on the stand.
  • The examiner field matters. Baked-in case metadata ties the image to who made it and when.
  • Best evidence = most complete. A physical image preserves the whole disk; defense experts can re-examine the same bits you did.

Check yourself

1. You can only make one image and want the most complete one. Physical or logical, and why?

Physical. It captures the entire disk including unallocated space and deleted files, which a logical image of a single volume omits.

2. The verify step reports a different SHA-1 than the acquisition hash. What does that tell you?

The image is not a faithful copy — data changed during or after acquisition (or there were bad blocks). It isn't trustworthy evidence as-is; re-image from a stable, write-blocked source.

3. Why is E01 preferred over raw dd for forensic work?

E01 stores verification hashes and case metadata inside the container and supports compression and segmentation, so the image is self-describing and self-verifying. Raw dd is just the bits.

4. What single piece of hardware keeps the acquisition from altering the original drive?

A write-blocker (hardware or software), which allows reads but prevents any writes back to the evidence drive.
