01Overview — what this lab is really teaching

Windows is constantly writing down what happens to it. Two logs in particular are a forensic diary: the USN (Update Sequence Number) Journal, an NTFS change log that records every file creation, deletion, rename, and modification; and the Windows Event Logs, which record logons, logoffs, password resets, updates, and hundreds of other system events, each tagged with an Event ID. Together they can place a specific action at a specific time — and the USN Journal catches deletions even when the deleted file itself is gone.

You'll open a pre-processed Autopsy case (parsed with the USN Parser and ParseEvtx modules), locate both log sources in the file system so you know where the data comes from, then read real events: logon/logoff (4624/4634), a password reset (4724), Windows updates (44/43), and a sequence of USN entries that reconstruct a folder being deleted and renamed into the Recycle Bin.

The payoff is that logs give you events with built-in timestamps — the richest possible fuel for the timeline work of Lab 14. The skill is knowing which Event ID means what, and reading the USN Journal's Change_Type and MFT references to follow a file's fate. The caution: logs roll over (old entries are overwritten) and can be cleared, so absence of a log entry is not proof an event didn't happen.

03Walkthrough

Task 1Locate both log sources

Know where the parsed data comes from before you trust it.

  1. Open the pre-processed case. USN Journal: expand to $Extend and find $UsnJrnl with its :$J and :$Max streams — compare sizes to confirm $J is the big one (the change records).
  2. Event Logs: Windows\System32\WinEVT\Logs\ — the three classics are Application.evtx, System.evtx, Security.evtx (older XP: config\*.evt).
    📸Screenshot for your report: The WinEVT\Logs folder listing the .evtx files.

Task 2Read Event Log events by ID

Each Event ID is a specific, documented event type.

  1. Results → Extracted Content → Windows Event Logs. Sort by Event Identifier, then (Shift-click) Event Time.
  2. Find 4624 (logon): the 2020-08-27 04:32:10 entry — note logon type 2 (interactive/network). Then 4634 (logoff) at 04:32:45 — the short gap suggests an automated setup login.
    📸Screenshot for your report: A 4624 logon event with its details pane open.
  3. 4724 (password reset attempt) at 04:38:58 — username, computer, SID.
  4. 44 (update download) and 43 (update install) — match a download to its install to see whether an update (e.g. Defender) actually applied.

Task 3Read USN Journal change records

Follow a file's fate via Change_Type and MFT references.

  1. Results → Extracted Content → NTFS USN Journal Entries. Note the Change_Type column (file_created; file_closed, file_deleted; file_closed, data_appended, file_new_name/old_name).
  2. Go to page 12 (end of journal). Sort by Filename. Find $I3L7INC (created, data appended) and $R3L7INC (a directory, renamed) at 2020-08-29 20:14:01 — the signature of a folder being deleted into the Recycle Bin (note the Recycle-Bin-style $I/$R names from Lab 9).
    📸Screenshot for your report: The USN entries showing the $I/$R rename sequence.
  3. Search Filename Temp: the directory entry with file_old_name confirms Temp was the folder's original name before the rename. Reconstruct: a folder Temp was deleted, renamed $R3L7INC, with an index $I3L7INC created alongside.

04Reference — key Event IDs and USN change types

Event IDMeaningLog
4624Successful logon (logon type matters: 2=interactive, 3=network, 10=RDP)Security
4625Failed logonSecurity
4634 / 4647Logoff / user-initiated logoffSecurity

7045New service installed (persistence)System
43 / 44Update install / downloadSystem/Setup

USN Journal change types

  • file_created; file_closed — a file was made.
  • file_deleted; file_closed — a file was deleted.
  • file_new_name / file_old_name — a rename (both halves recorded).
  • data_appended / data_overwrite — content changes.
  • MFT Reference / Parent MFT Reference tie each change to a specific file and its folder.
Watch out

Logs roll over — the USN Journal and Event Logs have size caps and overwrite oldest-first. An event not in the log may simply have aged out. And Event ID 1102 (log cleared) is itself evidence of tampering.

06Manual corrections & currency notes

The NDG manual was written in 2020–21. These are the places where it is wrong, inconsistent, or out of date — worth knowing before you trust a screenshot.

WhereThe manual saysWhat's actually true
Parsing toolsUSN Parser + ParseEvtx in AutopsyBoth fine. Current go-tos: Eric Zimmerman's MFTECmd (USN/$J) and EvtxECmd (event logs), plus Chainsaw/Hayabusa for rule-based event-log hunting at scale. Autopsy's modules are a solid baseline.
Event ID coverageA handful of IDsReal exams watch many more: 4688 (process creation), 4698 (scheduled task), 7045 (service install), 4672 (special privileges), 1102 (log cleared). Microsoft publishes the full catalog — don't rely on memory.
Log sourcesUSN + classic three event logsModern Windows has hundreds of event-log channels (PowerShell Operational, Sysmon if installed, TaskScheduler, TerminalServices) that are often richer than the big three. Sysmon especially is gold when present.
Journal retentionTreats the USN Journal as completeThe $J stream is capped and rolls fast on busy systems — it may cover only hours or days. Grab it quickly; don't assume it reaches back to the event you want.

07Making it defensible

Logs are high-value because they're timestamped and specific — but they're also finite and forgeable:

  • Read the Event ID precisely. 4624 with logon type 2 vs type 10 (RDP) vs type 3 (network) tell very different stories. Cite the type, not just the ID.
  • Absence is not proof. Logs roll over and can be cleared (watch for 1102). Say 'no record found', and note retention limits.
  • Correlate. A single log line is a lead; a USN deletion + a Recycle Bin artifact (Lab 9) + a timeline position (Lab 14) is a case.
  • Attribute to account, then person. A 4624 names an account and SID, not necessarily the human at the keyboard.
On the stand

'The log shows my client logged in at 2 a.m.' — but which logon type (was it even interactive)? Was the account the client's? Could the log have been cleared or rolled? Precision about Event ID semantics, retention, and account-vs-person is what makes log evidence hold.

09Check yourself

1. What does Event ID 4624 record, and why does its logon type matter?

A successful logon. The logon type tells you how the user authenticated — e.g. 2=interactive (at the keyboard), 3=network, 10=RDP — which can be the difference between someone physically present and a remote connection. Cite the type, not just the ID.

2. Where is the USN Journal stored, and what forensic advantage does it offer over looking at files directly?

In the hidden $Extend\$UsnJrnl, as an ADS whose $J stream holds the change records. It logs creations, deletions, and renames — so it can show that a file was deleted (and its original name, via file_old_name) even when the file itself is gone.

3. Why is the absence of a log entry weak evidence that an event didn't happen?

Logs have size caps and roll over, overwriting the oldest entries, and they can be deliberately cleared (Event ID 1102). So a missing entry may simply have aged out or been wiped — you report 'no record found', not 'it didn't happen'.

4. You see USN entries creating $I3L7INC and renaming a directory to $R3L7INC, with a prior name of Temp. What happened?

A folder named Temp was deleted into the Recycle Bin: it was renamed to the $R-prefixed name and an $I index entry was created alongside it — the same $I/$R pairing seen in modern Recycle Bin forensics (Lab 9), reconstructed here from the change journal.
