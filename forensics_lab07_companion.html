01Overview — what this lab is really teaching

When a file is deleted, its directory entry vanishes but its bytes usually linger in unallocated space until overwritten. Data carving recovers those bytes with no file-system help at all — by recognizing files from their signatures (header and footer byte patterns) rather than from any directory that points to them.

You'll carve three files by hand in HxD — an XLSX, a PDF, and a JPEG — finding each header and footer, selecting the exact byte range, and saving it out. Then you'll do the same job automatically with Autopsy's PhotoRec carver and compare. The manual pass is the point: once you've hunted headers and footers by hand, you understand exactly what the automated tool is doing — and why it sometimes fails.

Carving's hard problems show up immediately. False-positive footers: FF D9 can appear inside a JPEG's own data, so the first match isn't always the real end. Headerless/footerless formats: some files have no clear end marker, so you carve to the end of the cluster and hope. And fragmentation: a file split across non-contiguous clusters can't be carved as one contiguous block — the deepest limitation of the whole technique.

03Walkthrough

For each file the recipe is the same: Find the header, note its start offset; Find the footer, note the offset of its last byte; Select block from start to end; Save Selection. Keep Offset base on Decimal.

Task 1Carve an XLSX

Office files (ZIP containers) have a clear header and a footer plus 18 trailing bytes.

  1. Open Lab007.001 in HxD (sector size 512). Set Offset base → Decimal.
  2. Search > Find > Hex-values → header 50 4B 03 04 14 00 06 00 → note start offset (6917632).
  3. Find footer 50 4B 05 06; the real end is that match +18 bytes (6931455).
  4. Edit > Select block → start 6917632, end 6931455 (dec) → File > Save Selection → Carved.xlsx. Open it to confirm (~14 KB).
    📸Screenshot for your report: The carved XLSX open without errors.

Task 2Carve a PDF (beware false footers)

PDFs can have multiple %%EOF markers; take the LAST one, and watch for false positives.

  1. Find header 25 50 44 46 (%PDF) — search direction All, since this file sits before the XLSX. Note start (3735040).
  2. Find footer 0D 0A 25 25 45 4F 46 0D 0A. The first hit may be a false positive — the true end has zeros filling to the end of the sector after 0A. Find Next until you reach it (6911314).
  3. Select block → Save Selection → Carved.pdf → open to confirm.

Task 3Carve a JPEG (false footers again)

FF D9 appears inside JPEG data; the real footer is followed by zeros to the sector end.

  1. Find header FF D8 FF E0 (direction Forward) → note start (6934016).
  2. Find footer FF D9; the first hit(s) are false positives inside the image data. Find Next until you see zeros to the sector end after D9 (6995053).
  3. Select block → Save Selection → Carved.jpg → open to confirm.
    📸Screenshot for your report: The carved JPEG rendering correctly.

Task 4Automate with PhotoRec in Autopsy

See the tool do in seconds what you just did by hand.

  1. New case → add NDG Lab7.001 → Configure Ingest → Deselect All → tick only PhotoRec Carver → Finish.
  2. Expand the volume to $CarvedFiles — here, 13 files carved from unallocated space (names are cluster-based, not original).
  3. Run Embedded File Extractor afterward to expand ZIP/Office archives into their contents. Compare these results to your hand-carved files.

04Reference — signatures and the limits of carving

TypeHeaderFooterGotcha
JPEGFF D8 FF E0FF D9FF D9 recurs inside data — real end has zeros to sector end.

GIF47 49 46 3800 3BShort footer — false positives common.
PDF25 50 44 4625 25 45 4F 46Multiple %%EOF — take the last, zeros follow.
ZIP/DOCX/XLSX/PPTX50 4B 03 0450 4B 05 06 + 18 bytesFooter isn't the file end — add 18 bytes.

Why carving is hard

  • Fragmentation is the killer: a file split across non-contiguous clusters can't be recovered as one contiguous block. Header-footer carving assumes contiguity.
  • Footerless formats (plain text, some containers) have no end marker — you carve to the cluster end and may get trailing junk.
  • Overwriting: unallocated space is reused over time, so the longer since deletion, the less likely a clean recovery.
  • PhotoRec names files by cluster, not original name — metadata that could rename them is sometimes embedded, often not.

07Making it defensible

Carved files come with no file-system provenance, so they need extra care:

  • Carved files have no path or timestamps from the file system — they were in unallocated space. Don't overstate when or by whom they were created.
  • Hash every carved file (Lab 20) so you can prove it hasn't changed since recovery.
  • Document the carve. Tool, offsets (for manual), and that the file came from unallocated space — this is what makes it reproducible.
  • Don't claim a carved file proves possession on its own. Corroborate with link files, registry, or browser artifacts before attributing it to a user.
On the stand

'This file was deleted — how do you know who put it there, or when?' A carved file alone can't answer that; carving recovers content, not context. Be precise about what carving does and doesn't establish.

09Check yourself

1. Why isn't the first FF D9 you find necessarily the end of a JPEG?

FF D9 can occur inside the JPEG's own compressed data as a false positive. The real footer is typically followed by zeros padding to the end of the sector, so you Find Next past false hits until you see that.

2. What single property of a file makes header-footer carving fail, and why?

Fragmentation. If the file is split across non-contiguous clusters, there's no single contiguous byte range between header and footer to carve — the technique assumes the file's bytes are contiguous.

3. Why do XLSX and ZIP files share the 50 4B signature?

Modern Office files (2007+) are ZIP archives internally, so they start with the ZIP 'PK' header. That's also why Autopsy's Embedded File Extractor can expand them into their component files.

4. A carved file has no file-system timestamps or path. What does that mean for your findings?

It came from unallocated space with no directory entry, so you can't state when it was created or who created it from the carve alone. You recover content, not context — corroborate before attributing it to anyone.
