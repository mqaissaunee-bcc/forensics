01Overview — what this lab is really teaching

Email is still the backbone of business communication — and the header on every message is a travel log. As a message hops from the sender's machine through relay servers to the recipient's inbox, each server stamps its own Received: line onto the top of the header. Read from the bottom up and you reconstruct the entire route, including the originating IP address, the authentication results that reveal spoofing, and a Message-ID that can prove whether an email was truly sent or merely drafted.

You'll open messages in Thunderbird (an offline MBOX client), save the raw header, read it by hand bottom-to-top, then parse a second header with the offline Email Header Analyzer for a tidy breakdown.

The core technique is simple and powerful: headers are read from the bottom up, because the oldest events (origination) are at the bottom and each hop stacks on top. Along the way you learn to spot SPF, DKIM, and ARC results (the authentication checks that catch forged senders), to read the first Received: line for the sender's real IP, and to use In-Reply-To / References to tell a fresh email from a reply or forward. The caveat threaded throughout: header fields below the first trusted relay can be forged, so trust is highest at the top (your own servers) and must be earned downward.

04Reference — reading a header

Read bottom-up, trust top-down

Each server adds its Received: line to the top, so the bottom is the origin and the top is delivery. Trust is highest at the top (your own/recipient's servers, which you control) and decreases downward — lines below the first trusted relay can be forged by an attacker.

Key fields

FieldWhat it tells you
Received: (first/lowest)Originating server + sender's IP. The single most useful line.
Message-IDUnique per message, set by the sending server. Proves an email was actually sent (not just drafted) and helps identify the origin.
In-Reply-To / ReferencesPresent on replies/forwards; give the Message-ID of the parent. Absent = composed from scratch.
SPFWas the sending IP authorized to send for that domain? Fail = likely spoofed.
DKIMCryptographic signature proving the message wasn't tampered in transit and came from the claimed domain.
ARCPreserves SPF/DKIM results across forwarding hops.
From / Return-PathDisplay vs envelope sender — a mismatch is a spoofing flag.

06Manual corrections & currency notes

The NDG manual was written in 2020–21. These are the places where it is wrong, inconsistent, or out of date — worth knowing before you trust a screenshot.

WhereThe manual saysWhat's actually true
Email formatsFocuses on MBOX via ThunderbirdStill common, but enterprise evidence is often PST/OST (Outlook/Exchange) or EDB (Exchange store). Individual messages come as EML/MSG. The header-reading skill is identical across all of them.
Webmail realityCentered on a desktop clientMuch email now lives in webmail/cloud (Gmail, M365) with no local database — acquisition shifts to API exports, mailbox exports, or legal process to the provider. Headers are still the analysis unit.
Authentication depthMentions SPF/DKIM/ARC lightlyThese are now central to spoofing analysis, plus DMARC (which ties SPF/DKIM to a policy). A 'DMARC: pass' vs 'fail' is often the deciding factor on whether a sender is forged.
Tool currencyUses a local Email Header Analyzer buildFine and private (offline). Online analyzers (MXToolbox, Google's Messageheader) are quicker but send data to a third party — the lab's offline approach is the privacy-safe one for real evidence.

07Making it defensible

Headers are strong routing evidence but partly forgeable — calibrate your confidence to where trust begins:

  • Trust from the top down. Your/the recipient's servers are reliable; lines added before the first trusted relay can be attacker-controlled. State which lines you trust and why.
  • An IP is not a person. The originating IP identifies a network endpoint at a time; attributing it to an individual needs ISP records and more.
  • Use SPF/DKIM/DMARC to assess spoofing rather than taking the From line at face value.
  • Keep the raw header. Parsers are convenient but your evidence is the original header text — preserve and hash it.
On the stand

'Couldn't this header be faked?' Partly — which is why you explain the trust boundary (top-down), cite SPF/DKIM/DMARC results, and treat the originating IP as a lead to corroborate with provider records, not as proof of who sat at the keyboard.

09Check yourself

1. Why do you read an email header from the bottom up?

Each server that handles the message adds its Received line to the top of the header, so the header stacks newest-on-top. The bottom is the origination and the top is delivery, so bottom-up reconstructs the chronological route.

2. Which single header line is most useful for identifying where a message came from, and what does it give you?

The first (lowest) Received line — it shows the originating server and the sender's IP address. It's the starting point for tracing the source.

3. How can you tell a header belongs to a reply or forward rather than a message composed from scratch?

Replies and forwards carry In-Reply-To and/or References fields holding the parent message's Message-ID. If those fields are absent, the email was composed fresh.

4. Why shouldn't you fully trust every line of a header?

Lines added before the first trusted relay can be forged by an attacker — trust is highest at the top (servers you control) and decreases downward. You verify sender legitimacy using SPF/DKIM/DMARC rather than taking the From line or lower Received lines at face value.
