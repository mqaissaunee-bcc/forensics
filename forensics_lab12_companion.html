Overview — what this lab is really teaching

An email's visible from/to/subject is the least of it. The header records every server the message passed through, timestamps, authentication results (SPF/DKIM/ARC), and a unique Message-ID — enough to trace a message to its source and judge whether it's genuine or spoofed. This lab reads a header by hand, then parses one with Email Header Analyzer.

Tools & environment

On CAINE: Thunderbird (stores mail in MBOX) to view and export the header, and the offline Email Header Analyzer (run via a local server.py) to parse it.

Header fieldTells you
Received: (multiple)The chain of servers, bottom = earliest; often the sender's IP
Message-IDUnique per email; helps prove it was actually sent, and trace the sender
In-Reply-To / ReferencesPresent only on replies/forwards — identifies the parent message
SPF / DKIM / ARCAuthentication checks that flag spoofing and tampering
Read headers from the bottom up

Each server prepends its Received line, so the oldest event (closest to the sender) is at the bottom and the delivery to the recipient is at the top.

Walkthrough

Task 1 — Read a header manually

1 View and save the source

In Thunderbird, open the email, More > View Source, and File > Save Page As to Working Folder/FOR_LAB_012/The deadline.txt. Open it in gedit.

2 Work bottom to top

At the bottom: the body and the familiar from/to/subject/date, then the Message-ID (domain + alphanumeric; no In-Reply-To here means it was composed from scratch). Moving up: the first Received line shows the sender's IP (174.128.225.186) and the first mail server, plus the DKIM and SPF results. Further up, each subsequent server and finally the ARC and delivery to the recipient.

Message-ID is a lie detector

It's generated by the sending server, so its presence helps prove an email was actually sent (not just a draft), and In-Reply-To/References reveal whether it's an original, a reply, or a forward.

Task 2 — Parse with Email Header Analyzer

In a terminal:

then browse to http://127.0.0.1:8080.

4 Analyze a header

Copy the full header of Fw: Re: The deadline (View Source → Select All → Copy), paste into the analyzer, and click Analyze This!. It lays out the servers, IPs, hop times, and (for this forwarded message) the In-Reply-To/References fields.

Why offline matters

Many header parsers are web services — pasting a real suspect's header into one leaks evidence to a third party. The offline analyzer keeps the investigation self-contained.

15 Now that we are at the bottom of the email, let us dissect the data we see and look at some metadata that is of great value to investigations. a. The first set of data is the email body at the very bottom, as seen in item 1 below. b. Next, let us look at the data highlighted as item 2. This is the metadata we typically see when we view the email normally; it contains the sender's and recipients' email addresses, the subject of the email, and the date that it was sent. c. Next, we have the Message-ID seen in item 3. Message-IDs are unique to each email and are usually a combination of a domain name and an alphanumeric value. A Message-ID can be used to help determine the original sender. A communication service provider can use this information to uniquely identify the email and learn the IP address of the sender. The Message-ID is created by the server that sends the email message, so it can help to prove whether an email was actually sent, or whether it was just a draft moved to another folder. Finally, Message-IDs can be used to determine whether an email was a reply, a forward or if it was created from scratch. Most email replies and forwards will have a field called In-Reply-To: and/or References that provide the Message-ID of the email that it is responding to or forwarded from. Since the email below does not have these fields, we know that it was made from scratch.

Why it matters in court

Headers authenticate and trace

A header can establish that a message was genuinely sent, where it originated, and whether it was tampered with or spoofed — all from metadata the sender rarely thinks about. Keep the analysis offline so you don't leak the evidence.

  • Source tracing via Received chain + sender IP.
  • Authenticity via SPF/DKIM/ARC.
  • Thread reconstruction via Message-ID and In-Reply-To.

Course relevance

Core to Module 11: E-mail and Social Media Investigations. Know header structure, reading bottom-up, Message-ID, and SPF/DKIM/ARC.

Check yourself

1. Why do you read email headers from the bottom up?

Each server that handles the message prepends its own Received line, so the earliest event (nearest the sender) is at the bottom and delivery to the recipient is at the top.

2. A header has no In-Reply-To or References field. What does that tell you?

The message was composed from scratch — it's not a reply or a forward.

3. What do SPF and DKIM results help an investigator determine?

Whether the email is authentic or likely spoofed/tampered — they're sender-authentication checks performed by receiving servers.

4. Why use an offline header analyzer rather than a web-based one?

Pasting a real header into an online service discloses evidence to a third party; an offline tool keeps the investigation self-contained and private.

Cheat sheet

Read a header

  • Bottom = oldest, top = delivery
  • First Received = sender IP + 1st server
  • Message-ID = proof of sending
  • In-Reply-To/References = reply/forward
  • SPF · DKIM · ARC = authenticity
