01Overview — what this lab is really teaching

RAM is volatile — but Windows spills some of it to disk. The pagefile (pagefile.sys) holds memory pages that weren't currently needed, and because it lives on disk, it survives a shutdown. That makes it a persistent echo of what was in memory: fragments of URLs, email addresses, chat text, login data, and even whole images the user viewed but never saved. By default Windows does not clear it on shutdown, so it's a standing source of volatile-style evidence.

You'll extract the pagefile with Autopsy, then run Bulk Extractor over it — a tool that scans raw data for recognizable features (emails, URLs, carved JPEGs) regardless of file-system structure — and review the results in Bulk Extractor Viewer: email and URL histograms that count occurrences, individual feature hits with their surrounding context, and carved images.

The lesson is that deleting a file or closing a browser doesn't purge what was in memory — the pagefile keeps a copy. The method is feature extraction over raw bytes: Bulk Extractor doesn't care about files or folders, it just finds patterns, which is exactly right for a pagefile that has no file-system structure of its own. The caution: pagefile fragments are out of context and unattributable in time — a URL in the pagefile proves the string was in memory at some point, not when, by whom, or in what application.

03Walkthrough

Task 1Extract the pagefile

It's a hidden system file in the volume root.

  1. New case → add Lab18.E01 → open vol2 and find pagefile.sys in the Listing pane (note the ~578 MB size — that's 578 MB of potential evidence).
    📸Screenshot for your report: The pagefile.sys entry showing its large size.
  2. Right-click → Extract File(s) → save to a Pagefile folder in the case Export directory.

Task 2Run Bulk Extractor

Scan the raw pagefile for features — no file system needed.

  1. Open Bulk Extractor Viewer → Tools > Run bulk_extractor.
  2. Set Directory of Files to the Pagefile folder, and an Output Feature Directory (a new 'Bulk Extractor Report' folder). Submit Run — it carves features into per-type .txt reports.
  3. Tip

    Bulk Extractor works on raw bytes, so it finds patterns even in unstructured data like a pagefile, a memory dump, or unallocated space — a different philosophy from file-based tools.

Task 3Review the feature reports

Histograms rank by frequency; context shows where each hit sits.

  1. Open email_histogram.txt: email addresses ranked by count. Click the top address (e.g. hotdog918@hotmail.com) to see every occurrence in the Referenced Feature pane.
    📸Screenshot for your report: The email histogram with a high-frequency address selected.
  2. Click one occurrence (e.g. offset 21513176): the File Content pane shows the surrounding bytes — here, a user-profile fragment with LoginTime (epoch), country, client IP and port. Toggle Text/Hex.
  3. Open url_histogram.txt: URLs by frequency — sites visited or accessed by applications, with familiarity implied by count.
  4. Review carved images: in File Manager, open the report's jpeg_carved/000 folder — images from memory, some partial (missing data shows as black).

04Reference — what the pagefile holds and what it can't tell you

Why the pagefile matters

  • It's RAM spilled to disk — so it survives shutdown and holds volatile-style data (URLs, emails, chats, keys, images) long after the apps closed.
  • Default Windows does not clear it on shutdown — a standing evidence source.
  • It captures things the user never saved: incognito browsing, decrypted content, pasted text.
  • Related files to grab too: hiberfil.sys (a full RAM image written at hibernation) and swapfile.sys (modern-app memory).

Bulk Extractor feature types

ReportFinds
emailEmail addresses (+ histogram by count).
urlURLs (+ histogram).
ccnCredit-card-number patterns (verify — false positives).
jpeg_carvedCarved images, including partial.

Watch out

Bulk Extractor is a pattern matcher — it produces false positives. Every hit must be verified against its File Content context before you rely on it.

07Making it defensible

The pagefile is a treasure chest of fragments — and fragments are exactly what's easy to over-read:

  • Fragments are context-free. A URL or email in the pagefile proves the string was in memory at some point — not when, by whom, or in which app. Say exactly that.
  • Verify every feature hit. Bulk Extractor false-positives; confirm each hit in its surrounding bytes before relying on it.
  • Note the pagefile's state. Size, location, and whether it was cleared all bound what your findings can claim.
  • Corroborate. Pair a pagefile URL with browser history (Lab 13) or a timeline (Lab 14) before attributing a visit to a user.
On the stand

A URL in the pagefile is compelling until the defense asks 'when was it there, and who put it in memory?' You can't answer from the pagefile alone — so present it as corroboration of memory-resident data, verified in context, not as proof of a timed user action.

09Check yourself

1. Why can the pagefile contain evidence of activity even after the computer was shut down?

The pagefile is RAM paged out to disk, and by default Windows doesn't clear it on shutdown. So memory contents — URLs, emails, chat text, images — persist on disk long after the applications closed and the machine powered off.

2. How is Bulk Extractor's approach different from a file-based forensic tool, and why does that suit the pagefile?

Bulk Extractor scans raw bytes for recognizable patterns (emails, URLs, images) without needing any file-system structure. The pagefile has no internal file system — it's a dump of memory pages — so feature extraction over raw bytes is exactly the right technique.

3. You find a URL in the pagefile. What can and can't you conclude from it?

You can conclude the URL string was resident in memory at some point. You cannot conclude when it was there, who put it there, or in which application — pagefile fragments are context-free and untimestamped. It's a lead to corroborate, not proof of a timed user action.

4. Besides the pagefile, name a more complete on-disk source of memory data and why it's better.

hiberfil.sys — written at hibernation, it's a full image of RAM rather than just the paged-out slice, so it's far more complete and can even be parsed by memory-analysis tools like Volatility. (A live RAM capture, Lab 2, is the most complete of all.)
